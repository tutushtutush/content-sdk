# content-sdk

The headless browser SDK for content-api: fetches content from the service's public delivery endpoint and hands **plain data** to a platform, which renders it with its own components. No UI,
no DOM, no runtime dependencies. It reports views and link clicks to content-api's events endpoint (feature 004); ranking is content-api's and comes later.

Read first: `.specify/memory/constitution.md`, then the current feature in `specs/`. Every change goes through the spec-kit lifecycle (`/speckit-specify` → `/speckit-plan` → `/speckit-tasks` →
`/speckit-analyze` → `/speckit-implement` → `/speckit-converge`).

Feature 003, the search option (`q` in the query of `fetchPage`, version 0.3.0), is merged and tagged `v0.3.0`, and content-api serves it since its spec 013. Feature 004, reporting views and link clicks (`watchView` and `trackLinkClick`, version 0.4.0, for content-api's events endpoint, spec 014 there), is built on the branch `004-view-events`; content-api serves it only after a tag and its own pin change, and nothing is tagged or pushed until the owner says so. **Feature 005 (the session id)**: `watchView` and `trackLinkClick` take an optional `sessionId` (1 to 128 characters, no NUL; `null` is none) that is sent as `session_id`, for content-api's stored visit reference (its spec 017); the platform supplies it on each call and the SDK makes none, keeps nothing between calls and has no default (constitution I and VI); a bad value is left out with one warning; no `event_id` is sent until 0.9.0 (the SDK does not retry; see feature 009); version `0.5.0`, built on the branch `005-session-id`; the owner tags `v0.5.0` after the merge and content-api takes the tag in its own spec. **Feature 006 (the sort option)**: `fetchPage` takes an optional `sort` (`popular`, `newest` or `oldest`, exactly, in lower case; anything else, an empty text included, is a `bad_query` naming `sort` with no request) and sends it as `sort`, for content-api's delivery sort (its spec 020, merged 2026-11-18); no `sort` sends none and keeps the service's order, the SDK adds no default and keeps nothing between calls, the cursor passes through unchanged (the service judges whether it fits the order), the script-tag loader needs no code; the SDK does not return the service's `view_count` (research R10, an open decision for the owner); version `0.6.0`, built on the branch `006-fetchpage-sort`; the owner tags `v0.6.0` after the merge and content-api takes the tag in its own spec. **Feature 007 (the item view count)**: each item now carries `view_count`, the service's whole number of 0 or more (content-api spec 019), spelled as the service spells it and passed on unchanged; it is required (owner's option A): a missing or bad value (not a number, negative, a fraction, above the largest safe integer) refuses the whole page as `contract_mismatch`, never a default and never a partial page; the SDK formats, sums and adjusts nothing, and the request, the loader and the events are unchanged; the exported `Item` type requires the field, so code that builds items by hand needs it; this resolves feature 006's research R10; version `0.7.0`, built on the branch `007-item-view-count`; the owner tags `v0.7.0` after the merge and content-api takes it in its spec 021 (directly, so one deploy brings both `sort` and `view_count`). **Feature 008 (external-reference events)**: `watchView` and `trackLinkClick` take, in place of an item with an `id`, an object with an `externalRef` (1 to 128 characters of `A-Za-z0-9_.:/-`, case kept), for things the platform keeps itself, such as Listings' live Telegram posts (content-api spec 022); the event then carries `external_ref` and no `item_id`; both given (a non-UUID `id` counts as given), neither, or a bad reference records no event and warns once without the value (`null` is not given); the options are unchanged, the SDK invents no placement, sends no `event_id` until 0.9.0 and has no prefix rule; the typed item parameter is a union so a call with neither fails to compile; the platform must supply a stable, public-identifiers-only reference (no email, name or anything that identifies a person) and fix its format early, because changing it later splits one thing's events in two; version `0.8.0`, built on the branch `008-external-ref-events`; the owner tags `v0.8.0` after the merge, content-api takes it in a pin-bump spec, and only then does the live script carry it. **Feature 009 (the event key)**: `watchView` and `trackLinkClick` take an optional `eventId` (1 to 128 characters of `A-Za-z0-9_.:-`, no slash; `null` is none) that is sent as `event_id`, for content-api's deduplication (its spec 016): the first stored event with a key wins and repeats are ignored, per platform across item and reference events; the platform supplies it on each call and the SDK makes none, keeps nothing and skips no call (research R4: no generated key, no in-memory record of what was reported, both left for the owner's decision); a bad key is left out with one warning that never shows it and the event is still sent, so it can be stored twice (owner, 2026-11-21); the README tells platforms to pass the same key on a repeat, never a fresh random one per call, never a key made of public values only (it could be forged to block theirs), and that a key is one event's, not a visit's (`sessionId`) or a user's (`actorRef`); version `0.9.0`, built on the branch `009-event-id`; the owner tags `v0.9.0` after the merge and content-api takes it in a pin-bump spec.
